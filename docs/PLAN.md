# RA3 Native (Android) — план і результати розвідки

Мета: запускати власну копію Red Alert 3 (1.12, російська) на Android без Winlator/Box64, з сенсорним керуванням.
Репозиторій не містить жодних файлів гри (ні `.game`, ні `.big`, ні згенерованого з них коду).

## Результати аналізу `ra3_1.12.game` (tools/analyze.cpp)

| Показник | Значення |
|---|---|
| Формат | PE32 x86, база 0x400000, без релокацій, не запакований |
| Код (.text) | 8.15 МБ, ~2.36 млн інструкцій |
| Функцій (рекурсивний спуск) | ~44 000 |
| Прямі виклики | 139 298 |
| Виклики імпортів | 3 374 (+128 jmp) |
| Непрямі виклики через регістр (віртуальні методи, колбеки) | 29 276 |
| Switch-таблиці (`jmp [reg*4+table]`) | 513 (4 554 цілей) |
| x87 (FPU) | 48 013 |
| SSE1 (скалярні float) | 147 608 |
| SSE2 | 5 |
| MMX | 53 |
| Доступ через `fs:` (TEB/SEH) | 33 |
| `cpuid` / `rdtsc` | 13 / 46 (частина може бути хибним декодуванням даних) |
| Імпортів у таблиці | 475 (MSVCR80 165, KERNEL32 152, USER32 61, WS2_32 36 …) |

Висновки:
- Жодного пакувальника. Нормальний MSVC-код, фіксована адреса: підходить для статичної рекомпіляції в 4 ГБ-вікно гостьової пам'яті.
- Плаваюча арифметика це майже лише SSE1 і x87: ніякого SSE2/AVX, тобто ARM64 NEON/FPU покриває все. Для x87 потрібна точна емуляція 80-бітних регістрів або перевірений компроміс (double): вирішити пізніше.
- 29 тис. непрямих викликів: потрібна таблиця «гостьова адреса → згенерована функція» (хеш або щільний масив за адресою).
- 513 switch-таблиць: розбирати окремо, інакше цілі переходу втрачаються.
- Решта «екзотичних» інструкцій (`in`, `out`, `int`, `iretd`, `cli`…) майже напевно випадкове декодування даних серед seed-ів з вказівників у `.rdata`/`.data`; перевірити точнішим відсіканням seed-ів.

## Архітектура

1. **Лифтер** (`tools/`): PE → список функцій → C (по функції на одиницю компіляції). Виконується в CI з файлом користувача, результат не публікується.
2. **Рантайм**: гостьова пам'ять (одне вікно 4 ГБ), регістри як локальні змінні, прапорці обчислюються ліниво, таблиця виклику за адресою, SEH через явний стек обробників.
3. **Шар Win32**: ~475 функцій (потоки/події, файли, віртуальна пам'ять, CRT MSVCR80 → власна реалізація, час, Winsock → BSD-сокети, IME можна ігнорувати).
4. **Графіка D3D9**: гра викликає лише `Direct3DCreate9`, далі COM-таблиці. Потрібен власний шар D3D9 → Vulkan/GLES. Шейдери: `D3DXCreateEffectEx` (.fx з `Shaders.big`) і байткод SM2/3. Кандидати (зі сумісною ліцензією): MojoShader (zlib: ефекти і D3D-байткод → GLSL), DXVK (zlib) як джерело ідей. Вирішити після досліду.
5. **Звук**: DirectSound (5 ординальних імпортів) → OpenAL Soft/SDL.
6. **Відео**: прямих імпортів Bink/Miles немає, формат і код треба знайти окремо.
7. **Сенсорне керування**: за зразком OpenRA-Android (Sdl2Touch): жести, HUD, камера (RA3 обертає камеру середньою кнопкою).
8. **Мережа**: GameSpy мертвий; мета — LAN і можливо власний лобі-сервер.

## Етапи

0. (готово) Розвідка: PE, імпорти, функції. Цей документ.
1. (готово) Завантажувач (runtime/): PE у 4 ГБ вікно, 475 імпортів прив’язані до заглушок, TLS розібрано; перевірено `loadtest` на ra3_1.12.game.
2. (готово) Лифтер: `tools/lift.cpp` (ціле, SSE1, x87, `lock`-атомики). 580 диференційних тестів проти справжнього CPU проходять (`tests/run_tests.py`). На ra3_1.12.game ~96–97% функцій лифтяться повністю; решта інструкцій це майже лише хибні декодування даних (in/out/int/lds/…), `pushfd/popfd`, `rcl/rcr`, `pushal`, кілька MMX. x87 реалізовано через double з округленням до float за керуванням точності.
3. Запуск до `main`: CRT-ініціалізація, перше вікно, логування імпортів, яких не вистачає.
4. Файлова система й `.big`-архіви, перші ресурси.
5. D3D9-шар: чорний екран → меню → місія. Паралельно звук.
6. Сенсорне керування, продуктивність, лаунчер (імпорт файлів гри через SAF, як у OpenRA-Android).

## Ризики (чесно)
- Обсяг: ~44 тис. функцій і весь D3D9/ефекти. Для порівняння, виграш у FPS сумнівний: гра на Winlator вже тримає 30 fps, що є внутрішнім обмеженням логіки.
- Тестувати можна лише на телефоні через CI: цикл довгий.
- Лифтер без еталона (Wine/емулятор) важко відлагоджувати: еталон треба збудувати першим.
- Юридично: генерований код є похідним від гри, тому його не зберігаємо в репозиторії і не розповсюджуємо.
